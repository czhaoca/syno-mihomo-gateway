# 网关面板

**网关面板**（`mihomo-panel`，compose 中的 `panel` 服务）是本栈的第三个
容器：一个小巧的 FastAPI 应用，掌管**分设备的动态策略**（把某台设备在
*full-tunnel*、*full-direct* 与默认路由之间切换，不用碰 `.env`，也不用
重启任何东西）以及**持久化的流量统计**。它把 SRC-IP 规则文件写进 mihomo
的配置卷，并经控制器 API 热重载它们——mihomo 本身从不会因为一次策略
变更而重启。

- Web 界面：`http://<PANEL_IP>:<PANEL_PORT>/ui/`（默认端口 8090），中英
  双语，仅同源访问。
- CLI：`gateway.sh policy --list` / `--set <ip> --mode full-tunnel|full-direct|default`
  （[CLI 参考](cli.md)）。
- HTTP API：[生成的参考](../panel-api.md)（仅英文）——只增不破的 `/v1` 契约。
- 体检：`companion_health`（面板停止或降级、采集器滞后、轮询过慢、`stats.db`
  接近上限，或 mihomo 内存超过阈值 ⇒ 告警）与 `policy_parity`
  （面板状态与 mihomo 规则出现漂移 ⇒ **错误，退出码 3**）。

## 策略变更如何生效

1. 一次修改（经界面、CLI 或 API 发起）到达面板，并按**失败即停**的方式
   校验（裸 IP 规范化为 `/32`，拒绝地址重叠，也拒绝目标为面板自身的
   地址）。
2. 期望状态被写入 SQLite（`policy.db`），随后渲染进
   `providers/dyn-full-direct.txt` / `dyn-full-tunnel.txt`（先写临时
   文件，再改名）。
3. 面板把对应的规则 provider PUT 给 mihomo 控制器，并重新读取规则条数
   进行核对（**count parity**）。响应中如实的 `applied` / `parity`
   字段会说明这次变更是否已经 LIVE 生效，而不仅仅是保存下来。
4. 应用失败时，面板会**失败即静态保持**：标记 `panel-apply-failed`
   被置位，webhook（若已配置）会触发，且 doctor 的 `policy_parity` 会
   持续报告漂移，直到某次应用真正收敛为止。

这些规则文件位于常规路由**之上**（就在局域网豁免规则
`GEOIP,LAN,DIRECT` 的下面），因此设备策略会压过 GEOSITE/GEOIP 路由，而
局域网目标则始终保持直连——一台 full-tunnel 设备仍然能够访问 NAS。

## 优先级与网段的关系

静态的 `.env` 网段（`FULL_PROXY_SOURCES`）仍然在部署时渲染；**动态条目
优先级更高**。界面上每一行设备都会显示其是否属于该网段，覆盖一个网段
地址前会要求确认（真正的日常翻转运维权威是面板，而不是 `.env`——网段
仍是那条声明式基线，即便面板被重置也留存不变）。

## Web 界面

一共四个标签页，而且**打开时停在「统计」**——打开一个网关面板时你想知道
的是网络正在发生什么，而不是先去改哪一行策略。

- **统计** —— 时间范围选择器（48 小时 / 7 天 / 30 天 / 长期按天）、流量
  折线图，以及按设备汇总的流量（别名会解析到每一行上）。落地时使用的
  范围来自 `stats_default_range` **设置**，而不是打包进前端的常量，因此
  修改它不需要重新发布面板。各类提示只在确实有话要说时才出现：采集空洞
  （如实呈现，绝不插值）、可归因到应用的流量占比连同该占比实际测量的
  窗口，以及在「按天」范围下——当你所查询的窗口内**「一天」的定义发生
  过变化**时的警告。

  每个范围都覆盖**完整的窗口**（在默认的保留设置下——见下文）。自 v1.11 起，每次轮询都会同时写入分钟行**和**小时行，
  因此 48 小时范围读取分钟行，7 天与 30 天范围读取小时行，而小时行已经包含最近
  48 小时。超过 90 天的小时会汇总为天行，因此「按天」范围读取天行，**再加上**
  尚未汇总的小时行，从而包含最近 90 天。尚未汇总的日期按当前的时区与日界划分——也就是它们汇总后将带上的
  标记——因此跨越日界变更的窗口仍会显示出接缝。（v1.10.3 之前由浏览器只挑
  一个层级来读，每个窗口最新的那一段会被悄悄漏掉。）API 以
  `range=48h|7d|30d|daily` 提供相同的预设；只带 `tier` 的请求仍像以往一样
  只读取那一张表。较粗的行不会被拆回更细的行，因此窗口仍止于其分辨率层级
  的保留期：若把 `PANEL_STATS_MINUTE_HOURS` 调低到 48 以下、或把
  `PANEL_STATS_HOUR_DAYS` 调低到 30 以下，48 小时或 30 天视图会像以往一样
  缩短到该保留期。
- **设备** —— 策略编辑器，含网段标记、覆盖网段地址前的确认，以及上文
  所述的下发状态标记。
- **审计** —— 借助服务端已有的 `offset` 每次翻一屏。低于 760px 时每条
  记录是一张带字段标签的卡片，高于该宽度则是表格。时间戳、地址与请求方
  IP 永远不会在词中间断行。只有最新一页会自动刷新：当新记录不断把行往下
  推时，按原始 offset 重新拉取会导致有的重复、有的被跳过，因此较旧的
  页面会明确显示「已暂停」，而不是在你眼皮底下重排。
- **设置** —— 时区、统计「一天」的起始时刻、落地时间范围，以及设备别名。
  每一项都会标明当前值是**你设置的还是继承来的**；清空某个字段表示恢复
  出厂默认值，而不是存入一个空字符串。

面板是由面板自身**同源**提供的单页应用，这也正是 API 完全不需要任何
CORS 响应头的原因。它**不发起任何外部请求**——没有字体、没有 CDN、
什么都没有——并且这一点是在真实浏览器中于运行时校验的，而不是靠读源码。
写操作需要令牌：第一次写入会提示输入 `PANEL_SECRET`，且令牌只保存在
该浏览器本地。

警告绝不依赖 `alert()`。浏览器可以为某个页面关闭弹窗，那样会悄无声息地
吞掉最要紧的那条消息——网关可能与面板所显示的并不一致。这些警告改为
在页内呈现：横幅在滚动时保持可见，并且是叠加显示，而不是覆盖掉一条你
还没读的消息。

## 设备名称（别名）

名称与路由策略是两回事：出厂的 `devices` 表要求每一行都带有 mode，因此
在那里为主机命名，就等于强行给它一个路由决策。别名因此存放在自己的
附属表中，以主机地址为键——无论一台设备是否带有策略，都可以为它命名。
命名不会应用任何策略，也不会触发 reconcile——一个标签本身没有任何需要
网关去*执行*的东西。

每个别名都会记录它**来自哪里**，而这一来源决定了谁可以覆盖它：

- **你手工输入的别名，优先级高于任何导入来源。** 同步会原样保留这些行，
  并逐条报告为 `skipped`。
- **这一后果是有意为之的，在使用前值得知道：** 一旦你在面板里为某台主机
  命名，它就不再跟随厂商侧后续的改名。要把这台主机交还给同步，请清除它的
  别名——或者在有人值守的情况下，用 `--adopt` 重新运行同步。
- 导入来源始终可以更新**它自己**写入的行，也可以认领来源未知的行（这种行
  只可能由省略了该列的原始 SQL 产生，因此不携带任何权威性）。

在宿主机上用 `gateway.sh alias --sync --from <来源>` 批量导入
（`--list` 打印已存储的内容）。内置两种来源：`unifi` 依据 `.env` 中的
`UNIFI_*` 读取控制器，`file` 读取 `<数据目录>/identity/aliases.json` 中的
`{"entries":[{"ip":…,"alias":…}]}` 文档——Nimbus 导出或手写清单走的也是
同一条路径。输出是**逐行台账**：`applied` / `unchanged` / `skipped` /
`rejected`；凡是遇到已有别名的行，还会一并报告已存储的别名与来源，因此一次
跳过会指名道姓地说明它拒绝覆盖的那个名字属于谁。（`rejected` 的行根本没有
到达存储，所以只带地址与原因。）跳过是设计中的拒绝而非失败，因此运行仍以 0
退出；而只给出总数，恰恰会掩盖该规则所要保护的那些行。

面板自身与厂商无关，且**从不持有厂商凭据**。
`POST /v1/identities/import` 只认识 `{ip, alias, source}`；面板镜像内不含
任何厂商代码。适配器运行在宿主机一侧，位于一个由面板镜像启动、仅被当作
python 运行时使用的**一次性容器**中，凭据经**标准输入**传入——绝不经命令行
（主机与容器两侧的 `ps` 都能看到 argv），也绝不进入容器的环境变量。
`alias --sync` 无论使用哪个来源都需要 root：它都要从仅 root 可读的数据目录
读取输入（`unifi` 读 `.env` 中的凭据，`file` 读同目录下的文档），并启动一个
容器——这超出了 `policy` 子命令“只访问面板自身带鉴权的 API”这一豁免所覆盖
的范围，其中 `unifi` 是最尖锐的情形，因为凭据还会离开本机。`--adopt` 还额外
需要 `--yes`，因为它是唯一可能覆盖人工输入名称的模式。

### 你看到的是哪一个名字

一个名字只有**一个家**。单个主机（`/32`）由它的别名命名——那是身份层的
名称：设备的策略被移除后它依然保留，而且你手动输入的名称优先于任何导入
来源。网段无法承载别名（别名以单个主机为键），因此 `devices` 行上随策略
而存在的 `name` 是它唯一可能的名字。

- **重命名会写入该地址所能承载的那一层**——只有一个控件，你无需做选择。
- **升级不会改变你看到的任何名字。** 旧版本中，主机可能还持有第二个、随
  策略而存在的标签；升级迁移会把没有别名的标签作为你自己的编辑移入身份
  层，把已被别名取代的标签以 `rename 'old' -> ''` 的形式移入审计记录——
  旧文本在那里仍可追回。每台设备升级前后显示的名字完全一致。

默认**校验 TLS 证书**。UniFi 控制台出厂使用自签名证书，因此对它的第一次
同步会有意失败；`.env` 中的 `UNIFI_INSECURE=true` 是显式的豁免开关——而不是
在一次携带凭据的调用上做静默降级。

## 部署

面板随本栈一起部署——`install.sh`（全新安装时）会询问 `PANEL_IP`（网关
子网上的一个备用局域网地址，已做冲突检查），并**生成 `PANEL_SECRET`**
（32 位十六进制字符）；升级安装则以同样的方式迁移已有的 `.env`，并把
`PANEL_IMAGE` 并入 `UPDATE_IMAGES`。在这些开关就位之前，compose 会
**大声报错失败**（`${PANEL_IMAGE:?}` / `${PANEL_IP:?}`）。镜像在 `acr`
模式下来自你自己的 ACR（由镜像流水线持续镜像同步），在 `docker` 模式下
来自你自己提供的 `PANEL_UPSTREAM`——每一个 `PANEL_*` 开关见
[配置](configuration.md)。

最小权限：容器以 uid 10001 运行，只挂载 provider 写入面以及它自己的
`state/panel` 子目录——绝不挂载数据目录根，也绝不挂载 `state/` 本身
（自动更新器的元数据存放在那里）。安装器会在 `compose up` 之前，把这两个
挂载点都交给该 uid 所有。

## 数据、留存与备份

`state/panel/` 存放 `policy.db`（设备策略 + 审计日志）与 `stats.db`
（流量历史，采集器停摆期间会留下如实的空缺行）。每次策略变更都会把已提交的
`policy.db` 在旁边快照为一份滚动的 `policy.db.bak-<时间戳>`
（`PANEL_BACKUP_KEEP`，默认 5）；`stats.db` 是派生历史，没有自动备份。
留存开关（`PANEL_STATS_*`）记录在[配置](configuration.md)；备份/恢复/
重置/清除的运维手册见[运维](operations.md)。

`stats.db` 保存的内容（自 v1.11 起）：

| 数据 | 保留 | 说明 |
|---|---|---|
| 每设备、每策略组的字节数，按分钟 | 48 小时 | 最新若干小时的更细粒度副本。 |
| 同上，按小时 | 90 天 | 每次轮询都会写入，因此始终完整。 |
| 同上，按本地日 | 730 天 | 超过 90 天的小时汇总为天。 |
| 每设备按出口节点、规则类型、类别、目的国家划分的字节数 | 90 天的小时 + 730 天的天 | 自 v1.11 起记录。对这部分流量，每个维度的合计都等于设备合计；如果时间窗口回溯到升级之前（或回溯到旧版面板运行的时段），其中的设备字节数没有维度记录。当前运行的 mihomo 版本不提供国家信息时记为 `unknown`。自 v1.12 起，类别是该流量主机名的粗分类（见[分类](#分类)）；v1.12 之前计入的字节，类别为空。 |
| 每设备按主机名、嗅探到的名称、目的 ASN、目的端口、应用（geosite id）划分的字节数 | 强制 7 天 | 仅在开启 `PANEL_STATS_DOMAINS` 时记录。没有任何开关能延长。应用 id 自 v1.12 起记录。 |
| 归因覆盖率（携带主机名的流量占比，按规则划分） | 强制 7 天 | 只有 GeoSite、GeoIP、RuleSet、Match 和 SrcIPCIDR 规则会保存规则内容（payload）。其他类型一律存为空，包括可能写出订阅服务器自身域名的 Domain 类规则。v1.11 之前写入的行会保留原有内容，直到过期或被清除。 |

mihomo 自身的流量（订阅拉取、健康检查）计在设备 `gateway` 名下。达到硬性大小上限（`PANEL_STATS_CAP_MB`）时，最旧的数据最先被裁剪，无论它在哪张表里。只有当一条 7 天数据与一条长期数据一样旧时，才先裁剪 7 天数据。

**在 v1.11 的统计库上运行旧版面板。** 面板可能被手动降级，也可能在健康检查失败后被更新器自动回滚。旧版镜像能打开这个统计库，并在 7 天、30 天和按天视图中把每个字节只计一次：v1.11 把自己的分钟行存放在单独的表（`stats_minute_v5`）中，因此不会重复计数。旧版镜像的 48 小时视图只读取它自己的分钟行，所以一开始是空的，随着采集逐渐填满。v1.11 再次启动时，会把旧版镜像在此期间采集的数据并入。旧版镜像做不到的，是维护它不认识的表：
- 它不会裁剪或清除自己不认识的表：自 v1.11 起的分钟层级、各维度表，以及 7 天类的 `stats_sniff`、`stats_asn` 和 `stats_port`；自 v1.12 起还有 7 天类的 `stats_app`。开启 `PANEL_STATS_DOMAINS` 时，这些 7 天类数据会保留超过 7 天，直到较新的面板恢复；较新面板的第一次维护（采集器运行时，大约在启动一分钟后）会将其裁剪。
- 它的大小上限只裁剪它自己的表。
- v1.11 之前的面板运行期间，各维度没有记录。v1.11 面板在 v1.12 的统计库上运行时会记录各维度，但类别为空：这些字节会被视为“未经词典统计”（`no_dictionary`），而不会被当作未归因。
- 对于只有一个尚未传输任何字节的连接的设备、策略组或时间桶，v1.11 之前的面板会以 0 / 0 列出。自 v1.11 起，这些行保留下来用于记录连接数，并在所有字节读取中被排除。

手动降级之前，请先调用 `POST /v1/stats/purge` 清除旧版镜像不认识的 7 天类的表：降到 v1.11 之前时用 `{"tables": ["stats_sniff", "stats_asn", "stats_port", "stats_app"]}`；从 v1.12 降到 v1.11 时用 `{"tables": ["stats_app"]}`（见[运维](operations.md)）。自动回滚无法替你做这一步，因此这些行会一直保留到较新的面板恢复。

## 分类

自 v1.12 起，面板会根据主机名把每条流量归入一个类别。词典分两级：

- **应用**：一个 geosite id，也就是 mihomo 在 `GEOSITE,<id>` 规则里使用的名称（`netflix`、`bilibili` 等）。它只保存在 7 天类中，因此只有开启 `PANEL_STATS_DOMAINS` 时才记录：一台设备用过哪些应用，若保存数月，透露的信息不亚于它的主机名。
- **粗分类**：20 个类别之一，长期保存在类别维度中：video、music、social、messaging、gaming、shopping、news、search、ai、developer、cloud、cdn、storage、productivity、finance、education、travel、ads、system、platform。`platform` 表示大型厂商的共享服务（账号、API、静态内容），这些服务不属于任何单一产品。

如实原则：

- 只有主机名能为流量分类：mihomo 报告的主机名，或者嗅探器恢复出的名称。路由规则永远不能。`GEOSITE` 或 `GEOIP` 命中只说明流量如何被路由，不说明它属于哪个应用。
- 两个应用共用的名称（例如公共 CDN 节点）按厂商标注，绝不猜测具体应用。如果也没有厂商拥有它，就保持未归因。
- 词典无法回答的流量（没有主机名，或主机名不在词典中）类别记为 `unknown`，即未归因。相当一部分字节可能根本不带主机名（在开发时实测的网关上超过一半），所以这往往是最大的一类。它是统计中固定的一部分，永远不会被并入某个具名类别。
- v1.12 之前计入的字节，或回滚后由旧版面板计入的字节，类别为空。它们从未经过分类，报告中如实标为 `no_dictionary`，而不是未归因。

`GET /v1/stats/coverage` 在其时间窗口内（最多 7 天）报告两项度量。`classes` 说明流量能否被分类（`hostname` / `ip_only`）。`dictionary` 说明词典识别出了什么：`app`（已分类，并保留了应用 id）、`coarse`（已分类，只保留粗分类）、`unattributed` 和 `no_dictionary`。两个列表各自合计为 100 %。`dictionary` 统计类别维度仍按小时保存的时段，从 `dictionary.oldest_bucket` 开始（`PANEL_STATS_HOUR_DAYS` 小于 7 时，更早的小时已汇总为天）。`dictionary.app_ids_kept` 表示当前是否保留应用 id；关闭开关之前保留的 id 仍会计入，直到其 7 天期满。`dictionary.version` 标明面板正在使用的词典。

词典基于 [v2fly/domain-list-community](https://github.com/v2fly/domain-list-community)（MIT 许可证）在某个锁定提交上的 geosite 列表构建，覆盖面板整理的 150 个 id；不在其中的应用保持未归因。词典随面板镜像发布，面板从不下载它。如需修改，请编辑 `scripts/ci/categories_regen.py` 中的整理表或锁定的提交，然后运行 `python3 scripts/ci/categories_regen.py --write`。它会获取锁定的源，也可以用 `--source <tarball>` 指定。CI 中的 `categories_check.py` 会拒绝手工编辑过的文件；见[开发](development.md)。

## Insights 读取接口

自 v1.12 起，除了[API 参考](panel-api.md)中列出的各视图读取接口之外，另有两个读取接口为 Insights 界面提供数据：

- `GET /v1/stats/breakdown?dim=...` 给出某个维度在一个时间窗口内的各个取值，从大到小排列。维度有 `exit`（出口节点）、`group`（策略组）、`rule`（规则类型）、`category` 和 `country`；开启 `PANEL_STATS_DOMAINS` 时还有 `host` 和 `app`。它接受 `range=`（或 `tier` 加 `since`/`until`）、`device`、`sort=total|up|down`、`limit`（1 到 200）和 `offset`。`total` 和 `total_rows` 覆盖整个窗口而不只是当前页；`tier` 标明实际读取的粒度：各维度没有分钟层级，所以 48 小时的读取按小时计。
  - 长期维度会报告 `unrecorded`：整个窗口内该维度没有记录的设备字节，来自 v1.11 之前、旧版面板运行期间，或只清除了某一张表之后。这些字节会如实标出，绝不会显示成流量变少。`window.oldest_bucket` 标明该维度的数据从何时开始，`window.truncated` 表示窗口回溯到了这之前。
  - `category` 的每一行带有 `class`：`coarse`、`unattributed`（取值 `unknown`）或 `no_dictionary`（空值，未经词典统计）。
  - 无论窗口要求多长，`host` 和 `app` 最多只回溯 7 天；`window.since` 标明读取从何处开始。开关关闭时，它们返回 `enabled: false` 且没有任何行。
- `GET /v1/stats/overview?range=...` 一次读取就给出首页所需的全部内容：合计、时间线、各维度的前几名、空缺和覆盖率，全部来自同一时刻。可以用 `device` 限定范围，也可以用 `category` 或 `host` 限定。对于某个范围，存储的表无法回答的部分为 `null`，并由 `unavailable` 说明原因。例如，一个类别没有出口节点或国家信息，因为各维度是分开存储的；覆盖率也只针对整个网关测量。限定范围时，`totals` 会带上该范围的 `window`。
- 在 breakdown 和 `/v1/stats/timeline` 上加 `format=csv`，会把同样的行导出为 CSV 附件（UTF-8，无字节顺序标记，首行为表头）。电子表格会当作公式执行的文本单元格，会在前面加上 `'`。各列如下：
  - breakdown：`kind,value,up,down`，`dim=category` 时另加 `class`。维度取值行的 `kind` 为 `value`；另有一行 `kind` 为 `unrecorded`（`value` 为空），给出该维度没有记录的设备字节。这一行覆盖整个窗口，因此只出现在第一页。开关关闭时，`host` 或 `app` 的导出只有表头一行。
  - timeline：`bucket,up,down`，按天的行另加 `bucket_tz,day_boundary`。
- `/v1/stats/gaps` 接受 `since` 和 `until`，只列出与某个窗口重叠的空缺。

这些接口以及其他字节读取接口，都不会列出没有传输任何字节的设备、策略组或时间桶。与所有统计读取接口一样，这些接口在局域网内无需认证即可访问，而且会显示哪些设备使用了哪些服务：**切勿把面板暴露到公网**（见“安全”一节）。

### Prometheus 指标

设置 `PANEL_METRICS=true`（见[配置](configuration.md)）后，面板会在 `/metrics` 提供 Prometheus 文本格式的指标；关闭时 `/metrics` 返回 404。其中包括：

- 按维度统计的字节计数，每个维度的取值放在一个标签中，另有 `direction`（`up` 或 `down`）：`insights_device_bytes_total{device}`、`insights_group_bytes_total{group}`、`insights_exit_bytes_total{exit}`、`insights_rule_bytes_total{rule_type}`、`insights_category_bytes_total{category}` 和 `insights_country_bytes_total{country}`。它们从面板启动时开始计数，因此重启会把它们清零（Prometheus 的 `rate()` 能处理这种情况），清除流量历史也会把它们清零。它们只统计统计库已提交的轮询；
- 采集器自身的指标，与 `/health` 报告的数值相同，均使用基本单位（字节、秒）：`insights_collector_*`、`insights_stats_*` 和 `insights_mihomo_*`。尚未测得的数值没有样本，绝不会显示为零。

任何标签都不会带有主机名、嗅探到的名称、ASN、端口或应用级 id。Prometheus 会把空的标签值当作没有该标签，因此空值会写成 `no_dictionary`（未经词典统计的类别）或 `none`（其他情况，例如没有任何规则决定的流量）。名称恰好为 `none` 的出口节点或策略组会与之共用同一序列；而类别不可能命名为 `no_dictionary` 或 `none`，因为词典自身的检查会拒绝把二者用作类别 id。

## 安全

- **绝不要把面板暴露到公网**——不要让 cloudflared（或任何隧道/端口
  转发）指向 `PANEL_IP`。面板按局域网专用设计：**即使修改被锁定，读取
  在局域网内也始终开放**，所以暴露到公网会泄漏你的设备策略与流量历史
  （自 v1.12 起细到每台设备使用了哪些服务），无论 `PANEL_SECRET` 多强都无济于事；而且 bearer 校验没有速率限制——
  对于修改操作，密钥的熵是唯一的抗暴力破解屏障。
- `/metrics`（开启 `PANEL_METRICS` 时）与所有读取接口一样在局域网内开放，并带有按设备统计的字节计数：只能从局域网抓取。
- 修改操作始终要求 `Authorization: Bearer <PANEL_SECRET>`；空密钥会
  拒绝所有修改（失败即停），而不会因此放行。
- 记录在案的后续工作（v1 尚未包含）：一项自动化的 doctor 检查——用于
  发现面板意外暴露到公网——将需要一个独立的 Cloudflare API 凭据与
  授权范围，因为这里的 cloudflared 运行在令牌模式下，它的入站映射对
  任何本地文件都不可见。在它出现之前，本节的警告就是唯一的控制手段。

## 采集器健康状况

`/health`（局域网开放、扁平键、只含数字、不含错误文本）报告统计采集器的状况。`null` 表示“尚未测量”，从不表示零。

| 键 | 含义 |
|---|---|
| `collector` | `ok`、`stale`（近期没有成功的轮询）、`off`（`PANEL_STATS_POLL_S=0`）或 `error`（统计库不可用） |
| `collector_lag_s` | 距上次成功轮询的秒数 |
| `collector_poll_ms` | 最近 30 次成功轮询（获取 + 写入）的平均耗时，毫秒 |
| `collector_conns` | 上一次快照中的连接数 |
| `collector_failed_polls` | 面板启动以来失败的轮询次数 |
| `collector_interval_s` | 面板实际使用的轮询间隔（`0` = 采集器关闭） |
| `stats_db_bytes` / `stats_cap_mb` | `stats.db` 的大小，以及面板实际使用的上限（`0` = 无上限） |
| `stats_db_growth_mb_day` | `stats.db` 在最近一天的增长速度，MB/天（采样满一小时之前为 null；清除后可能为负） |
| `mihomo_mem_mb` / `mihomo_version` | mihomo 的内存占用与运行版本，每分钟读取一次 |

`collector_interval_s` 和 `stats_cap_mb` 超出了工单所列的七个遥测键。有了它们，doctor 和发布验证脚本比较的是面板自己报告的数字，而不是重新读取 `.env` 中的开关——面板解析这些开关的方式可能不同，或者 `.env` 已被修改却尚未重新部署。

`GET /v1/stats/self` 以时间线形式提供同样的指标，每分钟一行，保留 7 天。可以像其他表一样清除（`stats_self`）。
