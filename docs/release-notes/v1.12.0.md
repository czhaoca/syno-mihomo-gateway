# v1.12.0 — Gateway Insights: categories and the analytics API (ships in v1.14.0)

Not published on its own: these changes reach users in v1.14.0, the first
release after v1.10.2. See [v1.14.0](v1.14.0.md) for the upgrade from v1.10.2
and the validation that covered this version.

The second slice of Gateway Insights. The panel now names what it sees.
Every flow with a hostname gets a category, and new reads answer the
questions the Insights screens will ask: top values, one-read landing
pages, CSV exports and an optional Prometheus feed. Nothing new appears in
the UI yet; the Insights screens arrive in v1.13.

## What's new

- **Categories.** A built-in dictionary files each flow under one of 20
  categories (video, music, social, messaging, gaming, shopping, news,
  search, ai, developer, cloud, cdn, storage, productivity, finance,
  education, travel, ads, system, platform). It goes by the flow's
  hostname, the host mihomo reports or else the name its sniffer
  recovered.
  - The category is kept long-term, in the category dimension.
  - The specific app (a geosite id such as `netflix`) is kept only in the
    seven-day class, so only with `PANEL_STATS_DOMAINS` on.
  - Only a hostname classifies. A routing rule never does, and a name two
    apps share is labelled by its vendor, never guessed.
  - A flow the dictionary cannot name is `unknown` (unattributed). It is a
    permanent class, and often the largest one.
  - The dictionary covers 150 apps from the geosite lists of
    v2fly/domain-list-community (MIT) at a pinned commit, and ships inside
    the panel image. The panel never downloads it.
- **Breakdown and overview reads.** `GET /v1/stats/breakdown` gives one
  dimension's values over a window, largest first and paged. It covers
  exit node, policy group, rule type, category and country, plus hostname
  and app with `PANEL_STATS_DOMAINS` on. `GET /v1/stats/overview` answers a
  landing page in one read: totals, the timeline, the top values, gaps and
  coverage, scoped to a device, a category or a host. Both say what they
  cannot know instead of showing a zero:
  - a dimension reports `unrecorded`: device bytes in the window it has no
    record of, for example from before v1.11;
  - the hostname class never reaches back more than seven days.
- **CSV export.** `format=csv` on the breakdown and on
  `/v1/stats/timeline`. Cells a spreadsheet would run as formulas are
  written as text.
- **Prometheus metrics.** With `PANEL_METRICS=true`, `/metrics` serves
  byte counters per device, policy group, exit node, rule type, category
  and country, plus the collector's own gauges. Off by default (then 404).
  No label ever carries a hostname, ASN, port or app id.
- **Coverage per class.** `/v1/stats/coverage` gains a `dictionary`
  section that splits the window's bytes four ways:
  - `app`: classified, with its app id kept;
  - `coarse`: classified, category only;
  - `unattributed`: the dictionary had no answer;
  - `no_dictionary`: counted before v1.12, or by an older panel.
- **Window-scoped gaps.** `/v1/stats/gaps` takes `since` and `until`.

## What changes for you

- **Category values.** From v1.12 a category is a category id, or `unknown`
  when the dictionary has no answer. An empty category means the bytes
  were counted without a dictionary, before this release or by an older
  panel after a rollback. Those bytes are never re-classified.
- **New knob.** `PANEL_METRICS` (default off). If you turn it on, scrape
  `/metrics` from the LAN only. Like every panel read it needs no
  password, and it shows per-device traffic.
- **Privacy.** With `PANEL_STATS_DOMAINS` on, the panel now also keeps
  which app each device used, for seven days, as it already did for
  hostnames. Nothing new is kept with it off.

## Downgrading, or an automatic rollback

The nightly updater can roll the panel back by itself when a health check
fails after an update. A v1.11 panel over a v1.12 `stats.db`:
- opens it unchanged. v1.12 adds one table (`stats_app`) and changes
  nothing else;
- cannot prune or purge `stats_app`. With `PANEL_STATS_DOMAINS` on, the
  app ids outlive seven days until v1.12 returns, and its first
  maintenance pass prunes them. A v1.12 read never returns them past seven
  days, even before that pass runs;
- writes every category as empty while it runs. Those bytes read as
  `no_dictionary` once v1.12 is back, never as unattributed;
- has no breakdown, overview or `/metrics` reads.

Before a downgrade by hand to v1.11, purge the app ids:
`{"tables": ["stats_app"]}`. For a downgrade below v1.11, follow the
v1.11.0 notes as well.

## Upgrading

Deploy the new panel image and recreate the panel container.
- From v1.11.x: the stats database migrates on first start (schema v6 →
  v7, one new table). `docker-compose.yml` gains one optional
  passthrough, `PANEL_METRICS`.
- From v1.10.x: the v1.11.0 notes apply as well. The migrations run in
  order on first start.

The UI ships inside the panel image, so an image that has not been
republished keeps serving the old panel.

## Validation notes

`validate_release.sh` phases **A6 and A6c are required gates**, on a panel
image built from the tag. In addition, record from the NAS during the run:
- `GET /v1/stats/coverage`: `dictionary.version` is set and
  `dictionary.error` is `null`, so the dictionary loaded inside the image.
  After a few minutes of traffic, note `dictionary.classes`, the app /
  coarse / unattributed / no_dictionary shares, in the brief's "Measured
  baseline".
- `GET /v1/stats/breakdown?dim=category&range=48h` and
  `GET /v1/stats/overview?range=48h` answer 200.
- With `PANEL_METRICS` unset, `GET /metrics` answers 404.

If the v1.11 validation reverted the poll default to 5 s (the #96
REQ-ADD), that revert must be merged into this release before it is
tagged.
