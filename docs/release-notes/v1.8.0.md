# v1.8.0 — the gateway panel (DRAFT until tagged)

Per-device routing policy you can change **live** — full-tunnel, full-direct,
or back to default, per LAN device, from a web page, the CLI, or an API —
plus persistent traffic statistics. No `.env` edit, no re-render, no restart.
A third container (`mihomo-panel`) joins the stack as a standard service.

## What's new

- **Gateway panel** (`http://<PANEL_IP>:8090/ui/`, bilingual): device rows
  with live mode flips, band badges, per-device traffic history
  (minute→hour→day rollups, capped, honest gaps), audit log.
- **CLI**: `gateway.sh policy --list` / `--set <ip> --mode …` — token-authed,
  exempt from `--yes`/root (it only talks to the panel's API).
- **Doctor**: `companion_health` (panel down/degraded ⇒ warn) and
  `policy_parity` (panel-vs-mihomo drift ⇒ **error exit 3**).
- **HTTP API**: additive-only `/v1` (generated reference: `docs/panel-api.md`).
- **Release gate**: `validate_release.sh` gains the REQUIRED A6 panel phase
  (health, sibling reach, LAN UI reach, per-mode routing proof from two
  distinct source IPs, restart persistence).

## The authority inversion (read this once)

Through v1.7.0, `FULL_PROXY_SOURCES` in `.env` was the only way to give a
device the full-tunnel treatment, and every change meant a re-render. From
v1.8.0 **the panel is the operational authority for day-to-day flips**: its
dynamic entries sit *above* the static band in the rule order and override
it per address. The band remains the declarative deploy-time baseline — it
still renders, still survives a panel reset, and the panel's UI warns before
overriding a band address. Nothing about your existing band behavior changes
until you create a panel entry for the same address.

## Upgrading from v1.7.0

1. Deploy the release as usual (`sudo sh ./install.sh` → redeploy). The
   precheck **migrates your `.env` automatically**: derives `PANEL_IMAGE`
   from your `REGISTRY_MODE`, generates `PANEL_SECRET`, folds the ref into
   `UPDATE_IMAGES`, and asks for exactly one new value — **`PANEL_IP`**, a
   spare LAN address for the panel's own network seat (validated and
   conflict-checked).
2. Compose is fail-closed on the new knobs (`${PANEL_IMAGE:?}`,
   `${PANEL_IP:?}`): an un-migrated `.env` refuses to deploy loudly rather
   than deploying half a stack — and every surface names the fix:
   `gateway.sh deploy|redeploy` refuse with a pointer at the installer
   migration, `doctor` reports `env: needs-migration`, the boot self-heal
   skips with a logged hint, and the nightly auto-update aborts with a
   notification saying exactly what to run.
3. The always-on dynamic rule layer (two `RULE-SET` lines + zero-byte
   provider seeds) renders for everyone; with no panel entries it matches
   nothing and the config behaves exactly as before.
4. The auto-updater now manages the trio as a quartet: the panel image
   updates with the compose set, health-gated (`/health` must report
   `db_ok:true` — a bare 200 is not health) with three-way rollback.

## Owner steps at release time

- Publish the panel image: run the sibling repo's `Panel Build` workflow
  (or let its daily schedule pick the tag up), and make the GHCR package
  public after the very first publish.
- Register the chosen `PANEL_IP` in your address/CIDR tracking.
- Never expose the panel beyond the LAN (reads are LAN-open by design; see
  `docs/panel.md` § Security).
