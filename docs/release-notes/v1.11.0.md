# v1.11.0 — Gateway Insights groundwork (ships in v1.14.0)

Not published on its own: these changes reach users in v1.14.0, the first
release after v1.10.2. See [v1.14.0](v1.14.0.md) for the upgrade from v1.10.2
and the validation that covered this version.

The first slice of Gateway Insights, the panel's traffic analytics. Nothing
new appears in the UI yet. This release rebuilds the stats store so later
releases can break traffic down by exit node, rule, country and category:
- the collector polls faster and costs about the same;
- the database keeps one table per dimension;
- the panel now reports on its own health.

## What's new

- **Faster, bounded collection.** The `/connections` poll now runs every
  2 seconds by default (was 10). A poll issues a fixed number of database
  statements however many connections are open, and an idle connection
  costs no write.
- **More facts per stats row.** Every row also records:
  - how many polls fed it;
  - how many connections it first saw;
  - its largest single-poll delta (a peak).

  A poll that follows a collection gap, a store's first poll, and a poll
  after the clock stepped back add their bytes but no peak. Rows from before
  this release read 0 there, meaning "not measured".
- **Per-dimension history.** Bytes are now kept per device by:
  - exit node (the node a connection actually left through);
  - rule type;
  - category;
  - destination country.

  They are kept for 90 days of hours and 730 days of days, like the device
  tiers. Category stays empty (not yet attributed) until the category
  dictionary ships. Country reads `unknown` while the running mihomo build
  does not report it (v1.19.32 does not).
- **Seven-day hostname-class tables.** With the opt-in
  `PANEL_STATS_DOMAINS` on, the sniffed name, destination ASN and
  destination port are kept beside the hostname, under the same forced
  seven-day retention.
- **Collector self-telemetry.**
  - `/health` gains flat keys: `collector_lag_s`, `collector_poll_ms`,
    `collector_conns`, `collector_failed_polls`, `stats_db_growth_mb_day`,
    `mihomo_mem_mb` and `mihomo_version`, plus `collector_interval_s` and
    `stats_cap_mb`, the cadence and cap the panel is actually using.
  - `GET /v1/stats/self` serves seven days of these gauges, one row a minute.
  - The doctor's `companion_health` now warns on a stale collector, a poll
    slower than half its interval, `stats.db` at 90 % of its cap, and mihomo
    memory above `PANEL_MIHOMO_MEM_WARN_MB` (default 512, `0` = off).
- **A scoped purge.** `POST /v1/stats/purge` takes an optional body:
  - `{"device": ...}` clears one device's rows;
  - `{"tables": [...]}` clears only the named tables;
  - `{"before": ...}` clears rows whose bucket starts before a moment;
  - the parts combine.

  An unknown key or table is refused with 422, and the reply counts the rows
  each table lost. The bare call clears everything, as before.
- **Faster stats views under load.** Stats reads no longer wait for the
  collector's write lock.

## What changes for you

- **`tier=hour` reads include the newest 48 hours.** The hour tier is now
  written at every poll, so a `tier=hour` request without `range` returns
  the same shape with more rows. The 7-day and 30-day views read the hour
  tier alone, and they were already complete since v1.10.3.
- **mihomo's own traffic** (subscription pulls, health checks) is counted
  under the device `gateway`. It used to be `unknown`.
- **Rule payloads stop naming hostnames.** `/v1/stats/coverage` now stores
  a rule's payload only for GeoSite, GeoIP, RuleSet, Match and SrcIPCIDR
  rules. Domain rules could name your subscription's own server. Rows
  written before this release keep their payload until they age out, within
  seven days. `POST /v1/stats/purge` with `{"tables": ["stats_coverage"]}`
  clears them at once.
- **The dimension history starts at the upgrade.** The exit, rule, category
  and country breakdowns cannot be recovered for traffic collected earlier.
  A window that reaches back before the upgrade holds device bytes the
  dimensions never saw.
- **Size cap.** When `PANEL_STATS_CAP_MB` is reached, the oldest data goes
  first, whichever table holds it. The 13 new tables and their indexes make
  `stats.db` grow faster than before. `stats_db_growth_mb_day` in `/health`
  shows the real rate.
- **The new memory warning.** `PANEL_MIHOMO_MEM_WARN_MB` is read by the
  doctor only. Raise it on a host where mihomo legitimately runs large, or
  set `0` to silence it.

## Downgrading, or an automatic rollback

The nightly updater can roll the panel back by itself when a health check
fails after an update. An older panel over a v1.11 `stats.db`:
- counts every byte once in its 7-day, 30-day and daily views. v1.11 keeps
  its minute rows in a table of its own (`stats_minute_v5`);
- starts its 48-hour view empty, and it fills as it collects;
- cannot prune or purge the tables it does not know. With
  `PANEL_STATS_DOMAINS` on, the seven-day `stats_sniff`, `stats_asn` and
  `stats_port` rows outlive seven days until v1.11 returns, and its first
  maintenance pass prunes them;
- lists a device, policy group or timeline bucket whose only activity was a
  connection that moved no bytes yet, at 0 / 0. v1.11 records such rows to
  keep their connection count and hides them from every byte read; an older
  panel reads them as stored, so its "no traffic in this range" state may
  not show for those windows.

Whatever the older image collects is folded back in when v1.11 starts
again. Before a downgrade by hand, purge the seven-day tables:
`{"tables": ["stats_sniff", "stats_asn", "stats_port"]}`.

## Upgrading from v1.10.x

Deploy the new panel image and recreate the panel container. The stats
database migrates on first start (schema v3 → v6): new tables, columns and
indexes only, nothing dropped, and the minute rows held move to the new
minute table with their hours completed. `docker-compose.yml` is unchanged. The new doctor knob
`PANEL_MIHOMO_MEM_WARN_MB` is optional. The UI ships inside the panel image,
so an image that has not been republished keeps serving the old panel.

## Validation notes

`validate_release.sh` phases **A6 and A6c are required gates**. A6c is new
and telemetry only. It checks:
- the panel's `/health` reports `collector=ok`;
- a mean poll of at most half the interval;
- a readable mihomo version;
- `stats.db` below 90 % of its cap.

It prints, for these notes, the raw numbers, the collection gaps recorded
since the run began, and the spread of the per-minute poll timings over the
run.

To be filled in at NAS validation (the #96 REQ-ADD), before the release is
published:
- `collector_poll_ms` quiet and busy (A6c's live figure and the per-minute
  spread over the run), and the `stats_gap` rows created during the run, each
  matched to the redeploy or A6's mihomo restart. A6c warns when a figure
  crosses the threshold below.
- If `collector_poll_ms` exceeds 500 ms at the production connection count,
  or a gap row appears with no real outage behind it, the default goes back
  to 5 s. That is `STATS_POLL_DEFAULT_S` in `app/config.py`, the
  `PANEL_STATS_POLL_S` line in `.env.example`, the row in
  `docs/configuration.md` (en+zh), and the "every 2 seconds" line in these
  notes. The panel image is built from the tag, so a revert means a new
  commit, a rebuilt image, and A6/A6c re-run on it before publishing.
- The measured `collector_poll_ms` replaces #94's estimate in the brief's
  "Measured baseline" (`docs/brainstorms/gateway-insights.md`), together with
  `stats_db_growth_mb_day` after a day of collection.
- After the panel starts, `stats_minute` is empty, which shows the fold ran.
