# v1.10.1 — the gateway survives a reboot

A patch release for one failure mode with no visible symptom: after a NAS
reboot the gateway could come back **green on every dashboard and routing
nothing**. The boot task now prevents the race that caused it, repairs a
lost one, and raises the DSM error mail if it cannot.

## What's fixed

- **The TUN dataplane survives a reboot.** On DSM, Container Manager
  autostarts mihomo (`restart: always`) at the same moment the Boot-up task
  runs. The task used to wait for Docker *before* creating `/dev/net/tun`,
  so mihomo could start first with an empty device bind: the controller
  answered, the dashboard stayed green, `doctor` reported a single
  `tun_gateway: broken`, and every LAN client was silently off the gateway
  until someone restarted the container. `setup_network.sh` now creates the
  device node as its **first** step — it needs nothing from Docker — and
  only then waits for Container Manager.
- **A lost race is repaired, once.** After the stack is confirmed up, the
  task verifies the dataplane: a mihomo whose controller answers but whose
  `mihomo-tun` interface is missing is restarted exactly once and
  re-verified. A controller that never answers is **not** restarted (that is
  a crash loop, not this race).
- **No more green outage.** If the dataplane is still not ready after the
  one restart, the boot task exits `2`, so a Boot-up task set to *Send run
  details only when the script terminates abnormally* mails the outage
  instead of a dashboard hiding it.
- **Two tunables, both optional.** `BOOT_HEALTH_RETRIES` (default `12`,
  × `HEALTH_INTERVAL` seconds to wait for the controller at boot) and
  `TUN_SETTLE_GRACE` (default `10` seconds the interface may lag the
  controller). The defaults suit a NAS; nothing needs setting.

## Upgrading from v1.10.0

**Refresh the release tree** — that is the whole upgrade. No container image
changed, `docker-compose.yml` is unchanged, and no new `.env` key is
required. The existing Boot-up task keeps its command; it picks up the new
helper at the next boot. To confirm the helper on the live stack without
rebooting, run it once by hand — it is idempotent and reports
`Ready. The gateway stack is up.` on a healthy gateway:

```sh
sudo sh scripts/setup_network.sh
```

Worth knowing:

- **Still on v1.10.0 and just rebooted?** If `doctor` shows only
  `tun_gateway: broken`, the remedy is `sudo docker restart mihomo`; see
  *TUN silently dead after a reboot* in the troubleshooting guide.
- Keep the Boot-up task **enabled**, running as **root**, and earliest in
  the boot order — the prevention lives in it.

## Validation

Validated on the production NAS before this release was published:

- **The full on-device gate** — deploy, split-horizon rendering, cold start
  with parked caches and black-holed tunnel resolvers, fail-closed long-tail
  DNS, LAN-client routing probes, the REQUIRED A6 panel gate (two-source
  policy-flip routing proofs + restart persistence), and the
  DNS_GEOIP_NO_RESOLVE round-trip — **57 passed, 0 failed, 0 warnings**.
- **The new boot helper, run once on the live stack:** every step a no-op,
  exit 0, `Ready. The gateway stack is up.`
- **A real reboot.** The Boot-up task created `/dev/net/tun` in its first
  second, 25 seconds before the Docker daemon was even reachable; mihomo
  then started with the device in place — `mihomo-tun` present, zero
  container restarts, no `Start TUN listening error` — and the doctor
  reported HEALTHY on all 23 checks with nobody touching the container.

Both CI surfaces (Woodpecker's 15 steps and the `panel-image` build check)
were green on the release commit before it was tagged. The panel image is
unchanged from v1.10.0 (`app/` is byte-identical), so no image was
republished.

The `-linux` assets remain **experimental** (no real-hardware validation).
